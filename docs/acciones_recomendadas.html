Track_sys - acciones recomendadas y ruta viable

Documento de trabajo para modernizar Track_sys legacy con foco en seguridad, migración a SQL y adopción de Docker sin hacer una reescritura kamikaze.

Situación actual: backend acoplado Riesgo: passwords en texto plano Destino recomendado: PostgreSQL + Docker

Hallazgos clave

  • Uso de MongoDB con conexiones repetidas por modelo.
  • Configuración hardcodeada en DB, puerto y URLs del front-end.
  • Rutas grandes con lógica de negocio mezclada.
  • Contraseñas sin hash en el flujo de usuarios.
  • Modelo con referencias manuales tipo next, before, last.
  • Falta de base sólida para contenedorización limpia.

Recomendación principal

Migrar gradualmente el núcleo transaccional a PostgreSQL y preparar una base de despliegue con Docker.

  • No hacer migración total en un solo paso.
  • Migrar primero el core comercial.
  • Refactorizar backend por capas mientras se migra.

Tecnología sugerida

  • Base de datos: PostgreSQL
  • ORM / migraciones: Prisma
  • Contenedores: Docker + Docker Compose
  • Hash de contraseñas: bcrypt

Acciones recomendadas

Prioridad Acción Motivo
Crítica Hashear contraseñas con bcrypt Evita almacenar credenciales en texto plano. Sí, eso había que hacerlo ayer.
Crítica Centralizar conexión de base de datos Reduce duplicación, facilita ambientes y mejora mantenibilidad.
Crítica Mover URLs, puertos y credenciales a variables de entorno Permite dockerizar y desplegar sin editar código por ambiente.
Alta Crear o recuperar package.json Sin eso, Docker y CI/CD quedan cojos.
Alta Diseñar esquema SQL para core del negocio El dominio actual es altamente relacional.
Alta Separar backend en routes, services, repositories Reduce acoplamiento y facilita la migración progresiva.
Media Agregar validaciones, logs y pruebas básicas Ayuda a evitar regresiones durante la transición.

Ruta viable

Fase 0 - Higiene mínima

Corregir seguridad y configuración: .env, conexión DB única, quitar IPs hardcodeadas y arreglar contraseñas.

Fase 1 - Docker para desarrollo

Levantar app + postgres con volúmenes para datos, uploads e imágenes.

Fase 2 - Esquema SQL inicial

Modelar empresas, usuarios, clientes, productos, pedidos, detalle, facturas y pagos.

Fase 3 - Migración del core comercial

Mover primero usuarios, empresas, clientes, inventario y pedidos. Ahí está el valor real.

Fase 4 - Refactor del backend

Reorganizar código en capas para que la base de datos no esté pegada con cinta a las rutas HTTP.

Fase 5 - Producción

Backups, endurecimiento de secretos, reverse proxy y despliegue controlado.

Ruta más pragmática

La vía más sana es crear una nueva capa o módulo para el core comercial usando PostgreSQL y mantener temporalmente Mongo solo donde todavía no se haya migrado.

O sea: modernizar con criterio, no con fe ciega y café recalentado.
