# Inventori Inventory Target UX / Domain Plan

Planning artifact only. No implementation is included.

Validation update by `sdd-planning-agent-9dcd4a` on 2026-09-17: repository evidence was re-checked against the current frontend/backend implementation before this document was accepted as the target UX/domain plan. The requested path `docs/ui-ux/inventory-current-state.md` is present under the application repository as `inventory-api/docs/ui-ux/inventory-current-state.md` from the current working directory.

## 1. Executive summary

Inventori should simplify the catalog/inventory/location mental model without hiding backend gaps:

- **Products** remain catalog records: what the company sells, buys, produces, subscribes to, or manages.
- **Inventory** becomes the operational/current-state area for physical stock: **Stock**, **Lots**, and **Movements**.
- **Locations** should replace the user-facing term **Bodegas** where the business means any physical or logical place stock can be held.

Recommended navigation direction:

```text
Main navigation
- Productos
- Inventario
  - Existencias
  - Lotes
  - Historial de inventario
- ...

Configuration / administration
- Ubicaciones
```

This direction is broadly compatible with the repository. Update: Product classification vs inventory behavior, explicit `controlsInventory`, non-inventory `No aplica`, non-physical products not using virtual warehouses, and `COURSES_VIRTUAL`/`AFFILIATIONS_VIRTUAL` legacy direction are resolved by `specs/non-physical-products-mvp/`. Remaining Inventory UX dependencies are physical stock-only/system-lot behavior, location editing/model details, and true transfers.

Implementation closeout update (2026-09-17): the coordinated `specs/inventori-product-inventory-master-plan/` implementation has now delivered the approved Product capability foundation, the Inventory workspace, transparent system-lot behavior, initial inventory, location lifecycle APIs/UX, allowed-location enforcement, adjustments, and true transfers. This document remains the target UX/domain plan; it is not a separate implementation specification and should not be used to reopen the approved source-spec decisions.

## 2. Current problems being solved

Evidence from `docs/ui-ux/inventory-current-state.md` and repository verification:

1. **Duplicated/fragmented inventory IA**
   - Root navigation exposes `Productos`, `Bodegas`, `Lotes`, and `Movimientos` separately in `src/public/root/manifest.js`.
   - Warehouse SPA exposes a separate stock view at `/warehouse/#inventory` in `src/public/warehouse/views/inventory.js`.

2. **Products are catalog-first but lack inventory onboarding**
   - Product UI form in `src/public/root/views/products-admin.js` does not expose `initialLots`, `allowedWarehouseIds`, `requiresLot`, `requiresExpiration`, or `lotStrategy`.
   - Backend accepts these in `src/schemas/product.schema.js` and `src/services/product.service.js`.

3. **Lots page mixes traceability with manual stock entry**
   - Root Lots view uses `GET /api/inventory/stocks`, `POST /api/inventory/entries`, and `PATCH /api/inventory/lots/:id/qa` through `src/public/root/inventory-api.js` and `views/lots-admin.js`.
   - This makes lots look like manually maintained master data rather than stock records generated by operations.

4. **Movements filters are ID-centric/backend-limited**
   - Backend route `GET /api/inventory/movements` only accepts `warehouseId`, `productId`, and `lotId` in `src/routes/inventory.routes.js`.
   - Repository filtering in `src/repositories/inventory.repository.js` confirms no date range, movement type, text, lot code, product code/name, or origin/reference filters.

5. **Warehouse model already has virtual types that conflate non-physical products with locations**
   - `src/lib/warehouse-types.js` includes `COURSES_VIRTUAL` and `AFFILIATIONS_VIRTUAL` descriptions for non-inventory offers.
   - This conflicts with the target domain rule: services/subscriptions/memberships are non-physical product types, not virtual locations.

6. **No edit/deactivate route for locations/warehouses**
   - `src/routes/warehouse.routes.js` supports only `GET /api/warehouses/company` and `POST /api/warehouses/company`.
   - `src/services/warehouse.service.js` supports list/create only.

7. **No true transfer flow**
   - Inventory entry schema includes reason `TRANSFER_IN` (`src/schemas/inventory.schema.js`), but `registerStockEntryInTransaction` in `src/services/inventory.service.js` creates an inbound lot and movement only.
   - No source-location decrement, paired movement group, or preserved lot movement exists for source→destination transfers.

## 3. Proposed information architecture

Recommended IA:

```text
Productos
  Catalog listing
  Product detail with compact inventory summary and "Ver inventario"

Inventario
  Tabs:
  - Existencias (Stock): current stock by product/location, primary operational state
  - Lotes: traceability/current lot state, not a primary creation workflow
  - Historial de inventario: read-only Kardex/movements

  - Ubicaciones: location master data replacing user-facing "Bodegas"
```

Reuse the current root shell rather than creating a separate app. Consolidate existing root Lots/Movements components into an Inventory workspace if feasible.

## 4. Product type model

Target product type is distinct from inventory control.

Recommended business-facing values:

| Product type | Controls physical inventory by default? | Requires location? | Requires business lot? | Notes |
|---|---:|---:|---:|---|
| Producto físico | Optional/commonly yes | Only if inventory-controlled | Optional | Can be lot/expiration-tracked. |
| Servicio | No | No | No | Should not show stock/lots/locations. |
| Suscripción | No | No | No | Future duration/periodicity out of scope. |
| Afiliación / membresía | No | No | No | Future validity attributes out of scope. |

Confirmed backend status:

- `Product.productType` is currently `String @default("FINISHED_PRODUCT")` in `prisma/schema.prisma`, not a validated enum for physical/service/subscription/membership.
- `src/schemas/product.schema.js` accepts `productType` as any string up to 50 chars.
- Existing service derives product types such as `FINISHED_PRODUCT`, `RAW_MATERIAL`, and `PACKAGING` from category in `src/services/product.service.js`; these are inventory/category classifications, not sellable-kind product types.

Resolved by `specs/non-physical-products-mvp/`: introduce explicit capability fields `productNature`, `controlsInventory`, `commercialBehavior`, and optional `entitlementKind`; preserve legacy `productType` but do not use it as source of truth for inventory/commercial behavior.

## 5. Inventory-control model

Target states:

1. Does not control inventory.
2. Controls inventory without business-visible lot tracking.
3. Controls inventory with lot tracking.
4. Controls inventory with lot + expiration tracking.

Confirmed backend status:

- `Product.requiresLot`, `requiresExpiration`, and `lotStrategy` exist in `prisma/schema.prisma` and `src/schemas/product.schema.js`.
- `lotStrategy` is currently constrained by API schema to literal `TRACKED` only.
- `registerStockEntryInTransaction` throws `Toda existencia requiere numero de lote interno` when no internal lot is provided (`src/services/inventory.service.js`).
- `createStockEntrySchema` also requires `internalLotNumber` for manual entries (`src/schemas/inventory.schema.js`).
- `Lot.internalLotNumber` is required and unique by company (`prisma/schema.prisma`).
- Agent-facing sellable product availability is currently derived from `warehouseLotStock` rows with usable lots in `src/repositories/agent-workspace.repository.js` and `src/services/agent-workspace.service.js`; therefore non-lot physical inventory cannot safely be introduced as only aggregate `warehouseStock` without updating sales/agent availability flows.

Recommended domain behavior:

- Users should never invent fake lot numbers for non-lot-tracked inventory.
- If backend retains mandatory internal lots, it should create **system lots** transparently for non-business-lot-tracked products, clearly hidden or labeled as system traceability in UI.
- Business-visible lot tracking should be controlled independently from internal traceability.

Backend dependency: either add supported system-lot behavior or change the stock model to allow non-lot stock. The smaller safe path is likely transparent system lots because current stock, movement, receipt, production, and QA flows already depend on `Lot`.

## 6. Physical vs non-physical product behavior

- Physical products may control inventory, require locations, require business lots, and require expiration.
- Services, subscriptions, and memberships should not create stock, lots, movements, or warehouse/location assignment.
- Non-physical products should display `Inventario: No aplica` rather than `0 stock / 0 lotes / 0 bodegas`.
- Do **not** encode services/subscriptions/memberships into virtual locations.

Repository conflict to resolve:

- `COURSES_VIRTUAL` and `AFFILIATIONS_VIRTUAL` in `src/lib/warehouse-types.js` currently describe virtual warehouses for non-physical offers. These should be deprecated for user-facing creation once product types exist.

## 7. Location domain model

Recommended user-facing concept: **Ubicación**.

Minimum attributes:

| Attribute | Meaning | Backend today |
|---|---|---|
| Name | User-facing name | `Warehouse.name` |
| Code | Stable code | `Warehouse.code` |
| Type | Business type/category | `Warehouse.warehouseType` enum currently warehouse/inventory-area oriented |
| Nature | Physical vs virtual/logical | `Warehouse.isVirtual` derived from type today |
| Sellable source | Can dispatch/sell from here | `Warehouse.isSellableSource` |
| Active | Can be used in new operations | `Warehouse.isActive` |

Recommendation: type and nature should become independent dimensions if the business needs virtual versions of several location types. Today they are coupled because `isVirtual` is derived from `warehouseType` in `src/services/warehouse.service.js`.

## 8. Warehouse/Almacén/CEDI/Virtual analysis

Business feedback examples should not become four separate entities. They are location types/nature:

| Business term | Recommended mapping | Notes |
|---|---|---|
| Bodega / Warehouse | Type = `WAREHOUSE`, Nature = physical | Current `GENERAL`, `RAW_MATERIAL`, `FINISHED_GOODS`, etc. may need mapping. |
| Almacén temporal | Type = `TEMPORARY_STORAGE`, Nature = physical | New enum/model value likely needed if business confirms. |
| CEDI | Type = `DISTRIBUTION_CENTER`, Nature = physical | New enum/model value likely needed. |
| Virtual location | Nature = virtual; type still describes purpose | For physical stock in logical state such as in transit/consignment if business confirms. |

Do not use virtual locations for services, subscriptions, or affiliations.

## 9. Product creation flow

Target high-level flow:

```text
Crear producto
  1. Información básica
  2. Tipo de producto
  3. Configuración de inventario (only if relevant)
  4. Existencia inicial (optional, only if inventory-controlled)
```

Rules:

- If product type is service/subscription/membership, inventory section is disabled with explanation.
- If product type is physical, ask whether it controls inventory.
- If it controls inventory, ask tracking level.
- If tracking includes expiration, require expiration on lot rows where stock is entered.

## 10. Initial inventory flow

Target onboarding flow:

```text
Create Product
  ↓
Does this product control inventory?
  NO → Finish
  YES
    ↓
Does the company already have stock?
  NO → Finish with zero stock
  YES
    ↓
Register initial inventory
  ↓
Save product + initial inventory in one transaction
```

For lot-tracked inventory, use a compact multi-row grid.

### Wireframe C. Initial inventory

```text
+ Existencia inicial ---------------------------------------------+
| ¿La empresa ya tiene existencias de este producto?              |
| ( ) No, iniciar en cero   (x) Sí, registrar ahora               |
|                                                                 |
| Total esperado: [250]                                           |
|                                                                 |
| Lote       Ubicación             Cantidad actual   Vencimiento  |
| LOT-A      Main Warehouse        80                2027-01-30   |
| LOT-B      Main Warehouse        120               2027-02-15   |
| LOT-C      Distribution Center   50                2027-04-01   |
| [+ Agregar fila]                                                |
|                                                                 |
| Suma: 250  Estado: OK                                           |
| [Atrás] [Crear producto y registrar existencia inicial]         |
+-----------------------------------------------------------------+
```

Confirmed backend support and caveats:

- `createProductSchema` supports `initialLots` and validates that `quantity` equals sum of initial lots (`src/schemas/product.schema.js`).
- `createProduct` loops initial lots and calls `registerStockEntryInTransaction` (`src/services/product.service.js`).
- It requires `inventory.manage` permission for initial lots.
- Caveat: service sends reason code `INITIAL_PRODUCT_STOCK`, but `createStockEntrySchema` does not list that enum; direct route validation does not apply inside service, yet movement reason values need standardization.
- Backend still requires internal lot numbers for every initial row.

Initial inventory should remain distinguishable from daily manual entry via reason/source (`INITIAL_LOAD` or a standardized initial-product-stock reason) and UI labeling.

## 16. Lot → Movement traceability

Selecting a lot should preserve context into movements without requiring IDs:

- UI can carry `lotId` internally but display lot code/name.
- Movement filters should show selected lot as `LOT-A / Shampoo A`, not numeric ID.
- Direct URL should be shareable where authorization allows.

Current gap: current Lots and Movements views are separate root views and lose context according to the current-state audit; backend supports `lotId` filter but UI needs contextual linking.

## 17. Normal receipt flow

Conceptual behavior:

```text
Purchase receipt confirmation
→ Stock increases
→ Lot is created/updated when applicable
→ Movement recorded
→ Receipt remains origin/reference
```

Current support:

- Purchase receipt models include `PurchaseReceipt`, `PurchaseReceiptItem`, `confirmedLotId`, `lotNumber`, and `expirationDate` in `prisma/schema.prisma`.
- Warehouse receipt UI exists under `src/public/warehouse/views/receipts.js`.
- Receipt service should be reviewed in the implementation spec for exact lot-creation behavior; this plan does not redesign receipts.

## 18. Production inventory behavior

Conceptual behavior:

```text
Production
→ Consume raw-material stock/lots
→ Produce finished product stock
→ Create finished-product lot when applicable
→ Record movements
```

Current support evidence:

- Production execution service exists at `src/services/production-execution.service.js`.
- Schema has production consumption/waste/return relations to `Lot` and production order origin/destination warehouses in `prisma/schema.prisma`.
- Detailed production redesign is out of scope; Inventory UX should display resulting stock/lots/movements.

## 19. Sale/dispatch inventory behavior

Conceptual behavior:

```text
Sale/dispatch
→ Consume/allocate stock
→ Consume/allocate lots when applicable
→ Record movements
```

Current support evidence:

- Dispatching UI exists at `src/public/warehouse/views/dispatching.js`.
- Inventory service includes reserve/release/dispatch functions and stock movement types `RESERVE`, `RELEASE`, `OUT` in `src/services/inventory.service.js` and `prisma/schema.prisma`.
- Order approval quantity/credit feedback is explicitly out of scope.

## 20. Transfer behavior and current gap

Target transfer behavior:

```text
Transfer
→ Decrease source location stock/lot
→ Increase destination location stock/lot
→ Preserve lot identity when business lot-tracked
→ Generate paired movements with same movementGroupId
→ Keep source/destination traceability
```

Confirmed current gap:

- `TRANSFER_IN` exists only as stock-entry reason in `src/schemas/inventory.schema.js`.
- `registerStockEntryInTransaction` creates a new inbound lot and `IN` movement; it does not decrement a source location.
- No transfer route/service found in `src/routes/inventory.routes.js` or `src/services/inventory.service.js`.

Classification: **new functional capability / backend domain change**.

## 21. Permissions

Current permissions:

| Capability | Current policies/evidence |
|---|---|
| View products | `products.view` or `products.manage` via `product.list/detail` |
| Manage products | `products.manage` via `product.create/update/delete` |
| View stock/movements | `inventory.view` or `inventory.manage` via `inventory.stocks.list`, `inventory.movements.list` |
| Manual entry/adjustment | `inventory.manage` via `inventory.entries.create`, `inventory.adjustments.create` |
| QA lots | `inventory.qa.manage` via `inventory.lot-qa.update` |
| View locations | `inventory.view`, `inventory.manage`, or `warehouse.receive` via `warehouse.company.list` |
| Create locations | `inventory.manage` via `warehouse.company.create` |

Recommendation: initially reuse existing coarse permissions:

- View inventory: `inventory.view`/`inventory.manage`
- Manage inventory/manual entry/initial inventory/transfers: `inventory.manage`
- View locations: current warehouse list policy
- Manage locations: `inventory.manage`
- QA lots: `inventory.qa.manage`
- View movements: `inventory.view`/`inventory.manage`

Avoid new fragmented permissions until workflows mature. Consider dedicated transfer/initial-inventory permissions later only if audit/compliance requires it.

## 22. Empty/loading/error states

- Products: show non-physical inventory as `No aplica`, not zeroes.
- Inventory/Stock empty: `No hay existencias para los filtros seleccionados.` with action `Entrar inventario` only if permitted.
- Inventory/Lots empty: `No hay lotes visibles para estos filtros.` Avoid prompting to create lots manually except initial/manual entry.
- Movements empty: `No hay historial para estos filtros.`
- Locations empty: `No hay ubicaciones configuradas.` with `Crear ubicación` if permitted.
- Loading: skeleton/table loading per existing root views.
- Errors: inline retry messages; do not expose internal IDs in user-facing recovery instructions.

## 24. Routes/components to consolidate or remove

Do not remove immediately; consolidate incrementally:

- `/root/#lots` → eventually `/root/#inventory?tab=lots`.
- `/root/#movements` → eventually `/root/#inventory?tab=movements`.
- `/root/#warehouses` → user-facing `/root/#locations` or renamed nav label; backend can remain warehouses initially.
- `/warehouse/#inventory` may remain warehouse-operator focused, but root Inventory should be the admin/management consolidated experience.

Use redirects/aliases to preserve bookmarks.

## 26. Data migration/backward compatibility

Recommended smallest safe path:

1. Keep database tables and backend entity names as `Warehouse` initially.
2. Change user-facing terminology to `Ubicaciones` where appropriate.
3. Add/rename frontend route aliases without breaking `/root/#warehouses`, `/root/#lots`, `/root/#movements` bookmarks.
4. Only introduce DB migration when domain decisions for type/nature are approved.
5. Map existing `WarehouseType` values to location labels.
6. Preserve all `warehouseId`, `lotId`, and `stockMovement` history.

Warehouse → Location can be done initially as UI/domain terminology without breaking inventory, provided DB/API identifiers remain stable. Actual enum/model extension requires migration and must preserve historical rows.

## 27. Risks

- Conflating product type and inventory control could recreate current confusion.
- Deprecating virtual course/affiliation warehouses may affect existing data if any tenant uses them.
- Backend mandatory lots can leak fake lot numbers into UX if system-lot policy is not designed.
- Location type/nature changes may break receipt/production/sales assumptions if done as a broad migration.
- True transfers are more than UI; implementing frontend-only transfer would corrupt traceability.
- Permission changes could unintentionally hide inventory from warehouse users.

## 28. Open decisions

1. Canonical product type enum and migration for existing `productType` values.
2. Whether inventory control is stored as explicit enum/fields or derived from product flags.
3. System-lot naming/visibility/audit policy for non-business-lot-tracked inventory.
4. Whether `allowedWarehouseIds` is an optional restriction and where it is enforced.
5. Location type catalog and whether nature is independent.
6. Which existing virtual warehouse types are deprecated vs migrated.
7. Edit restrictions for locations with stock/history.
8. Transfer API contract and movement semantics.

## 29. Recommended implementation phases

Adjusted phase plan based on repository dependencies:

- **P0 — Domain decisions and terminology guardrails**
  - Decide product type taxonomy.
  - Decide inventory-control/system-lot model.
  - Decide Location terminology vs actual DB migration.
  - Deprecation plan for `COURSES_VIRTUAL`/`AFFILIATIONS_VIRTUAL` as product-type workarounds.

- **P1 — Inventory IA consolidation (mostly frontend)**
  - Create Inventory workspace with tabs using existing stock/lots/movements APIs.
  - Preserve contextual navigation by query params.
  - Add product detail inventory summary and `Ver inventario`.
  - Improve user-facing filter chips while still using IDs internally.

- **P2 — Product onboarding + initial inventory**
  - Expose inventory-control choices once backend decisions are approved.
  - Use `initialLots` where business lot-tracked.
  - Add system-lot/non-lot behavior only after backend support.

- **P3 — Locations UX and editing**
  - Rename Bodegas to Ubicaciones in UI.
  - Add location edit/deactivate API and rules.
  - Add approved location type/nature model changes if required.

- **P4 — Transfers**
  - Implement balanced transfer backend/API.
  - Add transfer UX from Stock.
  - Validate paired movements and traceability.

Answers:

1. **Can this implementation spec be written safely now?** A P1 Inventory IA/frontend consolidation spec can be written safely. A full Products + Inventory + Locations implementation spec should wait for P0 domain decisions.
2. **Which domain decisions must be resolved first?** Product type taxonomy, inventory-control/system-lot behavior, location type/nature model, allowed-location semantics, and virtual warehouse deprecation.
3. **Which backend changes are unavoidable?** Product type validation/modeling, non-business-lot/system-lot support, location editing, true transfers, and richer movement filters if required.
4. **Which changes are frontend-only?** Inventory tabs over existing stock/lots/movements, Product → Inventory contextual links using IDs, terminology-only `Bodegas`→`Ubicaciones`, non-physical display suppression once product type is present in data.
5. **Can Warehouse → Location be done without breaking existing inventory?** Yes as a UI terminology/route-alias change while preserving `Warehouse` tables/API IDs. Model extension requires migration but can be deferred.
6. **How should non-physical products behave?** They should not control inventory, require locations, create lots, or use virtual warehouses. Show `Inventario: No aplica`.
7. **How should inventory-controlled products without business-visible lots work?** Prefer backend-generated transparent system lots while keeping business lot fields hidden; do not force fake user-entered lot numbers.
8. **Is initial inventory already sufficiently supported by backend?** Sufficient for explicit lot-tracked initial inventory with internal lot numbers, but not for non-lot visible inventory; reason-code and UI permission handling need alignment.
9. **What is required for true transfers?** A backend transfer service/API that validates source stock, decrements source, increments destination, preserves lot traceability, and creates paired movements with a shared `movementGroupId`.
10. **What should be deferred to later specs?** Sales/order approval stock availability, requested quantity modification during approval, customer credit/debt, subscription duration/periodicity, membership validity/duration, and advanced WMS operations.
